# API routing boundary

The compatibility API keeps its existing paths and operation metadata while
route registration is split into bounded `APIRouter` instances.  The registry
is defined in `dispatch_center.api.routers` and included by `app.main` after
the application middleware, static mount, and legacy handlers have been
constructed.

| Router | Compatibility surface |
| --- | --- |
| `auth` | `/`, `/auth/*` |
| `servers` | `/servers*`, `/server-config*` |
| `nodes` | `/nodes*`, `/node-agent*` |
| `identities` | `/identity/*`, project memberships |
| `projects` | project CRUD, records, files, run profiles, dispatch policies |
| `operations` | health, readiness, metrics, execution control, events, audit |
| `engineering` | engineering tasks, coding agents, coding runs |
| `inventory` | inventory scan and candidate operations |
| `datasets` | datasets and dataset snapshots |
| `runs` | jobs, dispatch, execution plans, and runs |
| `approvals` | approval listing and approve/reject actions |
| `agent` | agent HTTP endpoints and `/ws` |

This is a behavior-preserving extraction stage.  Existing handler bodies still
use the compatibility application state and are migrated to service/dependency
boundaries in later PRs; the route ownership and registration boundary is now
explicit so that new endpoints cannot silently attach to the monolithic app.

## Error and correlation contract

Newly migrated use cases can raise `dispatch_center.api.errors.APIError`.
Its public response shape is:

```json
{
  "error": {
    "code": "plan_digest_mismatch",
    "message": "Execution plan verification failed",
    "request_id": "<server-generated UUID4>",
    "details": {}
  }
}
```

The `X-Request-ID` response header is attached to every HTTP response,
including early authentication and 404 responses.  IDs are generated by the
Control Plane; untrusted caller-supplied values are not reused.  Legacy
handlers retain their historical `{"detail": ...}` body until their use case
is explicitly migrated.

## Compatibility checks

`tests/test_router_extraction.py` verifies that HTTP and WebSocket decorators
are not added directly to `app`, that every bounded router is registered, and
that the expected operation count remains stable.  The OpenAPI hash test also
guards paths, methods, schemas, and operation metadata during subsequent
handler extraction.
